## 问题与目标用户
- 要解决的问题：
  - 此前启动资料不完整，配置模板中全是占位符，无法直接投入使用；
  - 目标与实现路径不清晰，任务包依赖人工手写；
  - 需要人工干预的环节多，包括每次会话需人工恢复状态、多会话之间的交接依赖人工操作。
- 目标用户 / 场景：使用本套件进行多会话任务编排与演进的开发者。最初形态为单机、离线单用户；当前支持 `local`（纯本地）与 `github`（多人协作）两种底座，底座选择见 [README.md](README.md) 第 2 节。

## 目标与非目标
- 目标：
  - **当前目标（2026-11-13，项目所有者）**：在安全边界内以尽可能少的人工干预持续推进“计划 → 真实 Agent 执行 → 验证 → 独立审查 → 安全合并 → 恢复 → 下一任务”；优先消除误阻塞与重复确认，不以流程数量替代实际交付。该闭环是目标，不代表已交付。
  - 历史目标（T-000B）：吸收 obra/superpowers 的方法论特性，转化为本套件自有的 prompts/ 与 templates/ 文件，具体包括：
    - brainstorming 式章程引导；
    - writing-plans 式计划拆解；
    - subagent 驱动执行；
    - 两阶段代码审查；
    - TDD；
    - 验证先于完成。
  - 上述特性不直接并入 superpowers 仓库，而是沉淀为本套件自有资产。
- 非目标（2026-11-13 起）：
  - 不接入任何插件市场；
  - 不引入任何第三方依赖；
  - 不开发托管式调度服务、SaaS 控制台或新的 Agent Runtime；
  - 不以治理文档数量或流程完整度替代真实可运行的交付闭环。

## 约束与假设
- 平台 / 运行时：套件自有脚本保持纯 Python 标准库，不引入任何第三方依赖。真实 Agent 执行依赖本机已安装的运行时（如 OpenCode）；其版本、平台与权限行为以实测为准，未实测项记为未知。
- 数据与隐私：套件内容保持项目无关、可复用，不绑定任何具体项目。
- 性能 / 可靠性：`local` 底座继续依赖既有 SQLite 状态层与路径锁机制保障多会话一致性；真实自动交付的可恢复性与并发边界以实际实现与证据为准。
- 需验证的假设（2026-11-13 更新）：真实 Agent 执行 → 验证 → 独立审查 → 安全合并的闭环能在安全边界内稳定运行，且每一步都有可核验证据；该假设仍在验证中，不因实验分支上的试跑而视为已交付。

## 架构决策与替代方案

> 2026-11-13 前记录的历史决策如下；当前方向决策见本节末尾。

- 决策：吸收 obra/superpowers 的方法论特性（brainstorming 式章程引导、writing-plans 式计划拆解、subagent 驱动执行、两阶段代码审查、TDD、验证先于完成），转化为本套件自有的 prompts/ 与 templates/ 文件；不把本套件并入 superpowers 仓库。
- 替代方案：并入 superpowers 仓库 —— 已否决。理由：
  - 官方基本不接受新的 skill 贡献；
  - superpowers 无持久状态层，并入必须砍掉本套件的 SQLite 状态与路径锁核心；
  - 离线单用户前提会被其联网插件体系破坏；
  - 演进节奏将受制于上游。
- 取舍 / 风险：自维护方法论文档的持续成本 vs 上游依赖风险；选择自维护，即接受文档自维护成本，换取对状态层、离线前提与演进节奏的完全控制。
- 决策（2026-11-13，项目所有者）：优先推进真实自动交付闭环，而不是继续堆叠治理规则。T-000B 的非目标“不编写‘计划→任务’转换脚本（CLI 已支持该流程，提示词层足够）”自本日起不再成立；目标是把计划推进到真实执行、验证、独立审查与安全合并，并保留可恢复状态与可核验证据。实现方式与验证结果以任务、审查和证据为准，本章程不预设实现细节。
