## 1. 问题、目标与非目标

### 1.1 问题

现行契约把 C1–C4 写成统一的派发前置硬门，但 C2 的措辞同时包含三层不同的意思：

1. 执行实例拥有**独立任务上下文**；
2. 实例之间**彼此不可见中间状态**；
3. **共享同一会话视为不通过**。

`templates/runtime-capability.md` 又用“scratch file 不可见”作为 C2 的示例。这三处没有区分：

- 默认情况下**不经请求的上下文串线**（必须避免）；
- 两个任务**共享同一可写会话状态**（必须避免）；
- 同一项目的受信任角色在明确授权后**主动交换任务数据**（正常协作，不应被判为 C2 失败）；
- 文件工作区隔离、凭据 / 权限边界（属于单独的安全问题，不是 C2 的同义词）。

同时，契约要求“逐条探测并留下证据”，但缺少一条跨 Runtime 可发现、可在几分钟内完成的真实探测入口。结果是：操作者要么跳过探测，要么把一次重型安全审计当成入门门槛。

### 1.2 目标（提案）

- 用一条**可发现**的入口指令，让宿主 Agent 通过它自己的真实子代理 / 会话接口执行最小 C1–C4 探测；子进程和合成 fixture 不得冒充真实子代理。
- 把 C2 的四个概念拆开定义，给出可观测判据与负向情形；把“受授权的跨会话通信”从“串线”中分离。
- 明确：正常项目作业中，探测**缺失 / `UNKNOWN` / `STALE` / 探针 `FAIL`** 是可见风险提示，不是默认阻断；但**真实调用失败**必须如实报告失败，不得伪称成功。
- 定义能力记录的语义版本、新鲜度、复用与旧记录处理；旧判据不得静默改标为新的 `PASS`。
- 明确 C1–C4 与任务锁、专属工作区、允许路径、G1–G6、Reviewer 身份、#170 模型 alias 证据彼此独立。
- 给出最小实施拆分、影响清单、迁移 / 回退，并区分已观测、计划与未知。

### 1.3 非目标

- 不在本任务修改 `docs/orchestration.md`、`templates/**`、`editions/**`、`scripts/**`、`tests/**` 或任何现行门禁。
- 不新增 Runtime、第三方依赖、托管服务或新的状态机。
- 不把 C1–C4 扩展成沙箱、凭据、Reviewer 独立性或模型身份的证明。
- 不创建 / 授权任何真实子代理；本文的探针只是设计描述。
- 不替 #170、#151、#149、#73、#158 作出结论或改变其状态。

## 2. 现行语义与提案语义必须分开

| 项目 | 现行（当前权威，未改变） | 本文提案（未生效） |
|---|---|---|

## 3. C2 的四个概念

### 3.1 定义与可观测判据

| 概念 | 定义 | 可观测判据 | 负向情形 | 不等同于 |
|---|---|---|---|---|
| **A. 独立任务上下文**（independent task context） | 每个任务 / 角色实例拥有自己的任务标识、输入、指令和可写状态；实例只收到自己的任务包 | 两个实例各自收到不同的 nonce / 任务标识；A 的指令中不出现 B 的任务内容；两者的产物分别落在自己的任务记录 / 工作区 | 同一个实例被两个任务同时复用；A 的输出未经交接就进入 B 的输入；两个任务共用一个可写任务状态 | 不等于“进程不同”或“模型不同”；也不证明文件 / 凭据隔离 |
| **B. 不经请求的上下文串线**（unsolicited cross-context bleed） | 一个实例的内容在**没有明确请求、授权或交接记录**的情况下出现在另一个实例的上下文或输出里 | B 在未被给予 A 的 nonce / 句柄时，不主动复述 A 的 nonce；运行时不会自动把兄弟会话的消息注入 B；跨任务复用同一会话时，B 的首轮输入不含 A 的私有标记 | 运行时自动广播兄弟消息；共享系统提示带入其他任务数据；上一任务的上下文被静默复用；B 在未授权时读到 A 的中间状态 | 不等于“A 被告知 B 的句柄并获授权后读取 B”——后者是 C |
| **C. 共享可写会话状态**（shared writable session state） | 两个实例写入同一个可变会话 / 会话存储，任一方都能改变另一方的输入、历史或工具状态 | 两个实例有可区分的会话 / 句柄标识；A 写入自己的 scratch 或消息后，B 的上下文不出现该内容；一方不能追加 / 修改另一方的会话消息 | 两个任务使用同一 session ID；共用同一个可变 scratchpad；一方能改动另一方的待执行指令或任务状态 | 不等于“能读取对方消息”；读取是通信，写入同一状态才是共享可写状态 |
| **D. 受授权的跨会话通信**（authorized cross-session communication） | 一个实例在明确授权范围内，对另一个具名实例执行读取或消息传递；通信的授权、目标、用途、范围和结果可追溯 | 存在授权记录（项目策略 / 任务包 / 操作者指令）、目标句柄、执行者、时间与数据范围；通信只发生在授权范围内；不产生权限升级 | 未授权读取敏感会话；跨信任域使用别人的句柄；借通信篡改审查证据或绕过路径锁；把“能访问”当成“应该访问” | 不等于串线，也不等于共享可写会话；更不等于文件路径权限或 Reviewer 独立性 |

### 3.2 提案判据

在**新的语义版本**下，C2 的判定建议如下（仅提案）：

- **`PASS`**：A、B、C 三项的默认隔离均可观测；D 不被要求失败。若 D 在明确授权下成功，只记录“受授权通信可用”，不把 C2 改成 `FAIL`；若 D 因访问控制被拒绝，也只记录“通信受限”，不因此判 C2 不通过。
- **`FAIL`**：可重复观测到 B（无请求串线）或 C（共享可写状态）成立；或两个独立任务实际上被同一个可写会话承载。
- **`UNKNOWN`**：只观测到“在明确给出句柄并获授权后可读取”，但没有证明默认串线或共享可写状态；或语义版本不匹配、证据不可定位、结果为空 / 有歧义。**不得把这种观察直接判为 `FAIL`，也不得判为 `PASS`。**
- **任务特有的强隔离**：敏感数据、跨信任域、盲审、独立模型等由具体任务单独声明并核验；它们可以要求比 C2 默认基线更强的条件（例如“禁止任何跨会话读取”），但那是任务策略，不是 C2 的全局定义。

### 3.3 协作与安全的边界

受授权通信不是无条件的：

- **授权必须有载体**：项目策略、任务包中的明确允许，或操作者对具体任务的明确指令；聊天里的一句“可以看看”不足以构成敏感数据的长期授权。
- **范围最小**：只读取完成任务所需的数据；不读取凭据、私有会话、其他任务的工作区或审查中的盲审材料。
- **可追溯**：记录谁在什么时间、用哪个句柄、为什么、读了什么范围；记录本身不得包含令牌、cookie 或客户数据。
- **不放宽其他门**：通信授权不授予写路径、不解除任务锁、不替代 G1–G6，也不证明 Reviewer 的底层模型独立。

## 4. 快速真实探测入口

### 4.1 一条可发现的入口

提案的规范入口是一条**宿主 Agent 可直接执行的指令**（不是新 Runtime、不是 shell 子进程）：

```text
运行 runtime-capability-probe（快速 C1–C4 真实探测）：只读、不修改项目文件、
不使用业务会话；用你所在 Runtime 的原生子代理 / 会话接口执行，并按
templates/runtime-capability.md 记录证据、限制与语义版本。
```

- 可发现位置（未来实施时）：`docs/orchestration.md` 的角色选择入口、`templates/runtime-capability.md` 的 “When to use”，以及各底座入口提示词中的同一条引用。
- 可移植基线：这段文字 + 下面的探针步骤即可运行，不依赖任何 Runtime 专有 API；有 API 的 Runtime 可以另做**可选适配器**，把同一流程映射到自己的 spawn / wait / cancel 接口。可选适配器不得成为其他 Runtime 的前置条件。
- 命名：入口名 `runtime-capability-probe` 只是提案标识；未来可以用同名提示词或可选 CLI 暴露，但不得把某个产品的命令硬编码成“所有 Runtime 都可用”。

### 4.2 宿主 Agent 的真实调用路径

| 层次 | 实际调用 | 记录要求 |
|---|---|---|
| 宿主主会话 | 操作者发出上面的入口指令；宿主 Agent 在自己的主会话中执行 | 记录 Runtime 名称 / 版本、edition、执行模式、权限范围、开始时间 |
| 子代理 / 会话接口 | 宿主使用它**原生**的子代理工具或会话 API（例如任务 / subagent 工具、session API）启动真实实例 | 记录实际工具名、返回句柄、句柄再次解析的结果；不得用 `python -c`、shell 子进程或临时脚本冒充 |
| 等待 / 取回 | 宿主的原生 wait / collect 能力，或轮询其会话 API | 记录状态、产物、退出等价物、证据位置 |
| 取消 / 清理 | 宿主的原生 cancel / interrupt 能力；没有就如实写 `UNKNOWN` | 记录取消请求与终局；清理结果单独记录 |

如果宿主没有真实子代理 / 会话接口，只能人工开新会话，则这不是 C1 `PASS`，应记录为 `manual-handoff`，并说明其余能力无法在本轮自动探测。

### 4.3 最少探针（建议 3 个真实实例）

目标是在一次会话、几分钟内覆盖 C1–C4 的最小证据，同时不把“更强的隔离 / 沙箱”伪装成已证明。

| 探针 | 目的 | 实际动作 | 覆盖 | 不覆盖 |
|---|---|---|---|---|
| **P1（成功 / 句柄 / 取回）** | C1 + C3 成功路径 | 启动一个只读子代理，给它唯一 nonce；要求它返回 nonce 与自身句柄；父会话记录句柄，再次解析同一句柄；等待并取回状态 + nonce + 证据 | 句柄可寻址、可再次定位；状态 / 产物 / 证据可取回 | 不证明取消、失败分类或沙箱 |
| **P2（隔离 + 取消）** | C2 默认隔离 + C4 取消 | 启动第二个只读子代理 B，要求它写一个自己的 nonce 到自己的临时上下文并等待；在 B 运行期间，P1 的 A 在**未被告知 B 句柄**的情况下报告是否看到任何外来标记；随后父会话明确授权 A 用 B 的句柄读取 B 的标记（可选通信观察）；最后取消 B，记录终局与清理 | 默认无请求串线、两个句柄可区分、受授权读取的可观测性、取消终局 | 不证明写入隔离的全部类别、不证明跨权限配置、不证明沙箱 |
| **P3（失败）** | C4 失败分类 | 启动一个只读子代理，要求它执行一个**确定失败且无副作用**的动作（或返回运行时定义的失败）；父会话记录失败状态与错误证据 | 真实失败与成功可区分；失败不被写成成功 | 不证明所有失败类别；供应商额度错误不等于产品失败 |

- 若 P1 的 A 可以顺便观察 B 的写入隔离：让 A 写自己的标记，再让 B 报告是否看到外来标记；这只增加一次消息，不增加实例。
- “受授权通信”是**可选观察**，不是 C2 的通过条件。它成功不判 `FAIL`，它被拒绝也不判 `FAIL`。
- 若 Runtime 无法在不产生副作用的前提下制造失败，P3 记 `UNKNOWN`，不伪造失败，也不把“没测”写成 `PASS`。
- 若 Runtime 无法取消或无法观察取消终局，P2 的取消部分记 `UNKNOWN`，并在风险提示中说明“取消能力未验证”；不影响已经观测到的 C1/C3 事实，但 C4 不能因此判 `PASS`。

### 4.4 停止条件、费用与清理

- **预算**：默认每个实例最多 120 秒、整轮最多 600 秒；默认最多 3 个真实实例（可选通信观察不新增实例）。超过预算立即停止并记录“超时 / 未完成”，不把超时当成成功。
- **停止条件**：
  - spawn 失败或没有返回句柄 → C1 `FAIL` / `UNKNOWN`（取决于是否观察到启动动作），其余依赖 spawn 的能力记 `UNKNOWN`，停止后续探针并给出风险提示。
  - P1 无法取回 nonce / 状态 → C3 `UNKNOWN`，不推断成功。
  - P2 无法并发启动 → C2 `UNKNOWN`；不要用单实例推断隔离。
  - P3 无法诚实制造失败 → C4 `UNKNOWN`。
  - 任何实例返回空结果、句柄失效或结果无法核对 → 如实记录为失败 / 未完成，不写 `PASS`。
- **清理**：取消仍在运行的探针；删除本次产生的临时文件 / 分支（若有）；确认没有留下业务会话或项目文件改动。清理失败要单独记录，不能省略。
- **正常作业继续方式**：探测缺失 / `UNKNOWN` / `STALE` / 探针 `FAIL` 时，提案语义是显示风险并允许在治理条件满足时继续获授权尝试；真实调用失败、权限拒绝、锁冲突或结果为空时，按实际失败处理，报告未完成，不冒充成功。

### 4.5 明确禁止的替代品

- 用 `subprocess`、本地脚本、单元测试 fixture、mock 子代理或“在同一个会话里自问自答”冒充真实子代理 —— 这些只能验证适配器代码路径，必须标记 `SYNTHETIC` / `FIXTURE`，不能产生 Runtime 能力 `PASS`。
- 用“提示词写了支持”推断运行时支持。
- 用一次成功调用推断所有任务、所有权限配置、所有版本都可用。
- 为了通过 C2 而关闭访问控制、共享凭据或把两个任务塞进同一个会话。

## 5. 证据、语义版本与新鲜度

### 5.1 记录字段（提案增量）

在现行 [Runtime Capability Record](../../templates/runtime-capability.md) 的字段上，建议增加：

| 字段 | 作用 | 缺失时 |
|---|---|---|
| `probe_kind` | `FAST`（本文的最小探测）或 `DEEP`（权限 / 沙箱 / 身份等完整核验） | 视为 `UNKNOWN`，不得当作 `FAST` 或 `DEEP` 的 `PASS` |
| `probe_semantics_version` | 本次判据的语义版本，例如 `c1-c4/2`；C2 的新四概念判据必须带新版本 | 旧记录 / 无版本记录按 §5.4 处理 |
| `c2_semantics` | 该记录使用的 C2 定义摘要或版本引用，便于区分旧“共享同一会话即失败”与新的四概念判据 | 视为旧语义，C2 不得 `PASS` |
| `runtime_id` / `runtime_version` / `edition` / `execution_mode` | 记录适用的确切环境；“latest”不是版本 | 缺任一字段 → `UNKNOWN` |
| `permission_scope` | 探测时实际观察到的读 / 写 / 命令 / 网络边界（只描述观察，不授权） | 不阻断记录其他行，但相关安全结论记 `UNKNOWN` |
| `probe_date` / `evidence_ref` | 当前 head / 记录可定位证据 | `PASS` 必须同时具备；否则 `UNKNOWN` |
| `limits` | 未覆盖的类别、已知抖动、环境差异、会使结论失效的条件 | 不能留空；空 `limits` 视为不完整记录 |

### 5.2 判定取值

- `PASS`：在指定 Runtime / 版本 / edition / 模式 / 权限下被真实观测，证据可定位，语义版本匹配，且在新鲜期内。
- `FAIL`：在指定范围内被真实、可重复地观测为不满足；必须写明“探针失败”与“真实业务调用失败”的区别。
- `UNKNOWN`：未探测、结果为空 / 有歧义、语义版本不匹配、证据不可定位、句柄失效、未来时间戳或无法判定。
- `STALE`：超出新鲜期，或 Runtime 版本 / edition / 执行模式 / 权限 / 取回机制发生变化。
- `NOT_APPLICABLE`：该能力对本执行模式不适用，且必须在 `limits` 写明理由。

`UNKNOWN` / `STALE` / `FAIL` 都不能写成 `PASS`；`PASS` 也不能反推未探测的类别。

### 5.3 快速探测 ≠ 完整安全 / 权限核验

| 维度 | 快速探测（FAST） | 完整核验（DEEP） |
|---|---|---|
| C1–C4 | 最小真实 spawn / 句柄 / 取回 / 终局 | 多次、多模式、多权限配置复测 |
| 隔离 | 默认无请求串线 + 可区分会话 | 写入隔离、文件系统、环境变量、凭据、网络、并发上限 |
| 权限 | 只记录本次实际可做什么 | 允许 / 拒绝边界、越权尝试、CI / 合并权限 |
| 取消 | 一次取消终局（可观察时） | 不同阶段取消、清理残留、超时与强制终止 |
| 身份 | 不涉及 | 可信底层模型身份（#170）、Reviewer 独立性 |
| 结论 | 只能支撑“最小能力可用 / 未知” | 才能支撑安全边界声明 |

快速探测的 `PASS` 不得被引用为沙箱、权限或身份证明；完整核验也不能把旧快速记录直接升级成 `DEEP`。

### 5.4 旧记录与迁移

- **无 `probe_semantics_version` 的旧记录**：记为 `LEGACY_UNVERSIONED`。C2 在旧语义下有歧义，必须 `UNKNOWN`，不得静默改成新 `PASS`；C1 / C3 / C4 只有在后续契约明确“语义未变”且 Runtime / 版本 / edition / 模式 / 权限全部匹配、证据仍可定位时才可复用，否则同样 `UNKNOWN`。
- **语义版本变化**：受影响的能力全部降级为 `UNKNOWN` 并重测；不受影响的能力可以保留自己的旧行，但不得用“其余仍然适用”替代逐行判断。
- **环境变化**：Runtime 升级 / 降级、edition 切换、执行模式变化、取回机制变化、权限配置变化、证据链接失效、探测失败或取消 —— 都触发重测。
- **复用**：按能力行复用，而不是按记录整体复用；每行保留自己的 `probe_date`、`evidence_ref`、`limits` 与语义版本。
- **历史不可改写**：旧记录保留原判据与原文；新结论用新记录 / 新行表示，并用 `supersedes` 指向旧记录。不得把旧 `FAIL` / `UNKNOWN` 编辑成 `PASS`。

## 6. 与任务锁、路径、G1–G6、Reviewer 身份及 #170 的独立性

| 机制 | 由谁判定 | C1–C4 能证明什么 | C1–C4 不能证明什么 | 本设计是否改动 |
|---|---|---|---|---|
| 任务锁 / 活动任务锁 | 任务载体与 `docs/orchestration.md` 第二部分 | 仅“能否启动并取回一个实例” | 不能代替锁、不能解除锁、不能证明两个任务不冲突 | 否 |
| 专属工作区 / worktree | 任务包与 Git 纪律 | 仅“实例能否被寻址和取回” | 不能证明文件系统隔离、不能证明写入不越界 | 否 |
| 允许 / 禁改路径 | 任务包 + 路径校验 | 不能 | 不能证明某路径被允许；能力 `PASS` 不是路径授权 | 否 |
| G1–G6 合并门 | `docs/orchestration.md` 第二部分 | 不能替代任何门 | 不能替代当前 head CI、Diff 审查、逐条验收 | 否 |
| Reviewer 审查质量 | Reviewer 证据与 Master 判断 | 不能 | 不能证明审查独立、充分或正确 | 否 |
| #170 可信模型身份 / alias | #170 的独立设计 | 不能 | 不能从模型 ID、family 自述、温度或 Prompt 差异推断底层模型独立 | 否 |

补充规则：

- **未知不等于安全**：`UNKNOWN`、空结果、未授权访问、句柄失效，都不得被描述为“安全”“已隔离”或“成功”。
- **能力记录不是权限授予**：`PASS` 只表示“观察到能做什么”，不授予写路径、命令、网络、CI 或合并权限。
- **受授权通信不放宽路径锁**：即使 A 被授权读取 B 的数据，A 仍不能因此写 B 的允许路径或绕过任务锁。
- **Reviewer 独立性单独判定**：C2 的 `PASS` 不证明 Reviewer 用了不同底层模型；#170 未解决前，额外 Reviewer 只能作为第二意见。
- **真实调用失败优先于能力标签**：本任务的 spawn / wait / collect 实际失败时，任务结果按失败 / 未完成报告，不能用“能力记录之前是 PASS”覆盖。

### 7.3 可移植基线与可选适配

- **基线**：纯文档 + 宿主原生接口 + 标准库；不需要新 Runtime、网络服务或第三方包。
- **可选适配**：有正式 API 的 Runtime 可以写适配器，把 spawn / wait / cancel 映射到本流程；适配器只报告观察到的事实，不推断、不授权、不创建 Agent。没有适配器的 Runtime 继续用入口指令 + 人工记录。
- **禁止**：把某个 Runtime 的接口名写进核心契约作为所有 Runtime 的必备能力；也不得因缺少适配器而把 `UNKNOWN` 写成 `FAIL` 或 `PASS`。
