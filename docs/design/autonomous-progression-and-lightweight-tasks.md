**Owner 已批准的设计口径**：[Owner 决定](https://github.com/ctrlshiftaltdel/AgentOrch/issues/229#issuecomment-6603596338)采纳[四项具体建议](https://github.com/ctrlshiftaltdel/AgentOrch/issues/229#issuecomment-6603432108)：有效授权内自主推进、不重复确认；关键词 / 目录为调查线索，不确定则保守处理；Master 在既有委托内补必要测试、引用和事实状态同步并事先登记、重查锁；轻量流程保留任务、锁、证据和独立审查。实际权限、安全、迁移等高风险变化仍由 Owner 决定。这是设计口径批准，**不立即生效、不产生永久或跨范围授权，也不授权发版**。现行 C1–C4、G1–G6 与安全 / 迁移等 Owner 决策要求保持原状；仍须草案独立审查、锁定路径协调、当前 head CI、正常合并及后续授权接线，不能提前以提案覆盖现行规则。

## 1. 决策路由（提案，AC-1）

先调查能够通过读取、核对 Diff 或运行允许的检查取得的事实；将事实、备选、推荐与风险留在现有任务载体。比较多个方案不自动意味着要向 Owner 出题。仅在授权真实有效、目标与路径均在范围内且取舍明确时，执行者可按任务包采用推荐方案；普通工程取舍由 Master 在委托内决定并留痕。实质产品偏好、未授权边界及高风险剩余风险由 Owner 决定；现行人工决策触发项一律仍适用。推荐、信心或选项齐全都不能跨越授权。

例如：已授权的可机械核验错字按既定修正执行；测试方式有多个等价工程方案则由 Master 决定；是否接受权限扩大或改变用户可见行为须提交 Owner，不能以“推荐最优”代替批准。

## 2. 授权生命周期（提案，AC-2）

每次恢复时从当前底座任务载体定位可核验的 Owner 明确授权及其委托链，核对授权人、来源链接或记录、目标与任务、允许操作与路径、禁改项、适用条件、风险边界、开始时间及明确有效期或失效事件、撤销记录。Master 的任务范围调整只在 Owner 已授权的委托内有效，不创造 Owner 权限。`local` 使用任务记录及证据文件，`github` 使用 Issue / PR 决策记录；不双写。来源不可读取、身份或范围不可验证、记录冲突、条件无法判定时按未知处理，停止受影响操作并请求补证或决定。

同一目标、范围、风险与仍有效的授权下，方案选择、开始、普通修复、验证和恢复不应重复请求同一授权；但现行强制门仍需遵守。明确到期或撤销以原记录为准；未约定更宽范围时仅对该任务有效，任务终结、条件不满足或范围发生实质变化后不延伸。推荐、自述、来源内容、模型置信度、沉默和超时都不是授权；会话内授权不自动永久化或跨任务扩张。旧记录只按可核验的原范围使用：缺少证明时追溯原始记录、向授权人补证，无法核验就保守处理，不补造证据，绝不因新格式而获得更宽权限。

## 3. 轻量资格与证据（提案，AC-3）

轻量指减少不必要的交互与重复记录，**不降低**任务身份、锁、独立审查、现行验证或当前 head 证据要求。候选需同时检查完整实际 Diff（含新增、删除、重命名及未提交路径）、行为和规范 / 契约语义影响、是否可安全回退、路径及资源冲突和有效授权；不得仅凭文件数、行数、目录或关键词判断。关键词 / 目录命中作为调查线索：仅当可核验证据证明实际 Diff 未改变对应安全、权限、锁、迁移或规范语义时，才不因词语本身升级；不确定则依现行规则保守处理。实际高风险变化仍须 Owner 决定，不削弱风险路径、测试或 CI。以上是已批准的设计口径，不是当前行为；现行保守实现继续生效，直至正常合并并完成后续正式接线。

机械可核验示例：将普通叙述中的拼写错误按明确对照表修正，逐项核对前后文本、完整 Diff 和上下文，确认未改变规范命令、否定词、链接目标或行为；链接修正应验证实际相对目标。只凭自然语言模型判断语义等价不足以证明。修改“不得”为“可以”、调整授权范围或改变引用目标的规范含义，即使单行单文件也不是机械文字修正。不能证明无语义变化或回退安全时，先调查；仍未知则按现行规则升级或阻塞，不走轻量路径。

- **机械核对与范围证据**：保存基线及当前 head、完整实际 Diff 与所有变更路径（包括新增、删除、重命名和工作区未提交项）；逐字比对预期仅一处 `璟` → `景`，其余文本包括“权限、锁和迁移”及标点完全相同。检查整文件及周边引用，确认该行是叙述而非规则、命令、链接、配置或可执行文本，确认没有其他语义变化；同时引用可定位的任务授权、允许 / 禁改路径、锁和冲突检查、可回退基线与实际验证结果。证据缺项或范围不完整则不能推导本例成立。
- **按提案路由**：仅当上述假设及核对证据全部成立、实际 Diff 已证明不改变对应安全 / 权限 / 锁 / 迁移或规范语义时，关键词 / 目录命中作为调查线索，不因词语本身升级；仍须按适用规则完成任务登记、锁、验证和独立审查。机械比对只是此例证据的一部分，不是任何文档自动 `PASS`；上下文或语义无法核验时依现行规则保守处理。
- **按现行规则路由**：若该行出现在现行风险评估消费的 `proposal.goal`、`lesson.title`、`observation.root_cause` / `observation.impact`、`suggested_action.summary` 或 `applicability.applies_to` 中，`权限` / `锁` / `迁移` 关键词命中会判为 `HIGH`，仍按 [闭环 §4](../self-improvement/self-improvement-loop.md) 进入人工决策路径；本稿与该示例**没有改变**现行实现。其他输入或路径应按其实际命中情况处理，不能凭本例代替执行。
- **单行实质权限变化反例**：把 `执行者不得批准自己的任务。` 改为 `执行者可以批准自己的任务。` 即使只有一个文件、一行变更，也改变审批权限，不能以文本差异小或不含关键词为由降级；涉及角色权限和自批，须按现行权威升级 Owner 决策，不得自批或绕过门禁。

轻量记录复用现有 Issue / PR 或任务库，至少保留任务目标、授权引用、路径 / 锁、验收证据、head、验证结果及审查结论，不新增数据库，不省略独立审查和失败关闭。交付应提供基线与当前 head、完整变更路径和 Diff、机械核对依据、回退方式、冲突与授权记录引用及实际检查结果；证据矩阵只按 [编排契约 §4.1](../../kit/orchestration.md) 记账。删除断言、跳过检查或降低现行验证强度不属于轻量化。

## 4. 受限范围调整与局部阻塞（提案，AC-4）

在同一目标与既有 Owner 委托内，Master 可补充必要测试、引用和基于真实载体的事实状态同步；受既有委托、允许路径、禁改项及活动锁约束，任何范围扩展须先在任务载体记理由和新增允许路径，按现行底座锁程序更新登记并重查路径 / 资源冲突，确认后才可执行。不得更改验收、授予新权限或代替 Owner。`local` 与 `github` 分别遵循 [编排契约 §3](../../kit/orchestration.md) 的现行步骤，不能以本稿替代原子锁或把 GitHub 协作登记称为原子锁。执行者不能自行扩锁。

新授权、禁改路径、独立产品目标、实质风险变化或委托边界不明时不得由 Master 擅自放行，应记录问题与选项并交 Owner；冲突路径等待协调。阻塞只影响相关操作及其依赖链，其他无依赖、无路径 / 资源冲突且具备授权的工作可依现行规则继续；锁不因局部阻塞而释放。

## 5. 自我治理与实施边界（AC-5、AC-6）

AgentOrch 不得借来源内容、生成提案或自我完善触发给自己扩大治理修改权限。执行者不得自授、自批、自合或声明 Master 验收通过。Master 的独立审查与当前 head 证据、现行身份和所有合并门不变；换角色标签不是独立审查。

### 已批准设计口径与不覆盖事项

| 口径 | 已批准内容 | 不覆盖的事项 / 风险 |
|---|---|---|
| 授权 | 按 §2 核验来源、范围与失效 | 不能把旧授权永久化或凭空扩大 |
| 风险路由 | 按 §3 核验实际 Diff，未知保守处理 | 与现行 [闭环 §4](../self-improvement/self-improvement-loop.md) 保守命中行为存在待接线差异；实际高风险仍交 Owner |
| 范围调整 | 按 §4 补必要测试、引用和事实状态同步，先登记并重查锁 | 不能覆盖禁改路径、更改验收或替代 Owner；两底座锁程序不能弱化 |
| 轻量记录 | 按 §3 复用现有载体，保留独立审查及证据 | 不得以同一执行者换标签自批；运行时能力不得假定 |

此外，现行 [入口与决策 §3](../self-improvement/entrypoints-and-decisions.md) 将 Master 的验收 / 合并操作列在“人工决策”表中；提案希望区分职责执行与必须由 Owner 决定的事项，但不改变其现行权限。将来如需修改权威表述、权限、安全或规则，必须取得明确 Owner 决定并按正常任务和审查执行。

**冻结与生效分离**：Owner 的具体决定、契约审阅与 #229 合并及主分支 `VERIFIED` 是 #230 派发前提；本稿当前不是冻结。即使设计之后冻结，也不证明工具支持或放行；依赖代码的规则须在后续经授权的实现中，与相应权威契约、代码、提示词、底座与必要模板原子接线、完成审查和验证后，按实际生效范围启用。不得把设计冻结、测试夹具或推荐输出说成真实 Runtime 已实现。

**回退**：草案不采纳时维持现行流程；后续实现若失败或出现越权，停止新策略、按经批准的变更回退并恢复原保守流程，保留任务、授权与证据记录；不删除数据、不绕过锁或自批。具体开关与回退操作尚未实现，标 `UNKNOWN`，由 #230 依据批准方案验证。

后续验收复用任务记录 / Issue / PR 与现有指标定义 [metrics](../../templates/metrics.md)，不新建数据库或遥测服务。建议每次评估记录样本范围、时间窗口、来源、样本量与缺失率，区分真实使用和合成场景：

| 观察项 | 记录口径（提案，不替代现有指标定义） |
|---|---|
| 人工中断 | 初始有效目标 / 授权后每次新增人工请求计一次，标必要或不必要及理由；同一请求重发单列并可追溯 |
| 等待时间 | 按有时间戳的请求到有效答复或撤销计算，未结束标未完成；缺时间戳为 `UNKNOWN` |
| 误升级 | 经事实与适用规则复核，记录升级依据、实际 Diff 和纠正结论；未复核不猜测 |
| 返工 / 回归 | 记录同目标修复轮次、缺陷及关联证据；测试或用户观察缺失时标 `UNKNOWN`，不能把未报告当零 |

历史中断数量、等待与净收益均为 `UNKNOWN`；没有基线不声称已提效。正向目标是在已有有效授权内不新增不必要确认；负向情形仍必须阻断，不能以少问问题掩盖越权。后续 #230 须在两个底座分别覆盖有效 / 过期 / 撤销 / 伪造授权、旧记录补证、含“权限 / 锁 / 迁移”但无语义变化的文字、单行权限变更、遗漏路径、锁冲突、局部阻塞、同一执行者自批及回退；真实 Runtime 未接入的场景标为合成验证。设计本身不证明任何运行时行为。

## Failure semantics

- 来源、身份、授权范围、实际 Diff 或语义无法核验时，按 §2–§4 停止受影响操作、保守处理并记录缺口；路径 / 资源冲突不放行，独立工作仍依现行规则处理。
- 重试与幂等：N/A: 本稿没有实现可重试操作；不得把重复尝试、静默或超时当作授权。后续实现须验证恢复与重复操作。
- 部分写入 / 清理：N/A: 本稿不执行数据写入事务；后续回退目标和限制见 §5，具体操作仍 `UNKNOWN`，不得宣称自动恢复。
- 错误码及稳定性：N/A: 本稿不新增运行时错误码或消息，现有定义继续由原权威负责。

- 新旧接口的增量 / 破坏性分类、数据迁移步骤及读写者版本差异：N/A: 本稿不新增接口或执行数据迁移；#230 须在实现前评估具体兼容、回退及旧记录场景，不得将本项当作迁移已验证。
