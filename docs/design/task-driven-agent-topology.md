## 1. 目标、边界与基本原则

目标：在保持 AgentOrch 的角色职责、权限边界、可追溯状态、独立审查和证据门禁不变量的前提下，由**具体任务**的性质决定调用 Skill、Tool、当前主 Agent、单独 Execution 实例、并行实例或独立 Reviewer，而不是先按岗位创建常驻 subagent。

原则：

1. **Role defines responsibility**：Master、Execution、Reviewer 是职责、权限、证据和签署者身份，**不是固定的进程数、模型实例数、岗位代理目录，也不是必须常驻的实例**；Role 与 Instance 的冻结关系见 §2.1。
2. **Task defines execution**：先形成可验收的事务边界；再判断哪些步骤由确定性代码/Tool 处理、何时加载 Skill、何时需要隔离上下文或并行实例；最后匹配角色/模型/Runtime。顺序固定为 **Task → Topology → 角色/模型匹配**；选择不是派发。
3. **Evidence defines completion**：完成由任务验收、真实执行结果、独立性要求与当前 head 的证据决定，不能依据 Agent 自述。
4. **Governance before optimization**：风险、权限、独立性、文件/资源锁与合并门是硬约束；只有通过硬约束的候选拓扑才能比较成本、耗时与成功率。
5. **Capability is not dispatch**：模型/子代理发现、候选排序、拓扑推荐不得冒充实际 spawn / wait / collect、授予权限、启动任务或通过审查。
6. **Runtime-neutral；探测风险可见，实际失败关闭**：AgentOrch 不自建新 Runtime / 网关；运行时适配器只报告可信能力事实。能力探测缺失、未执行、`UNKNOWN`、`STALE`，或探针 `FAIL` 但未证明宿主工具客观不存在时，**只记录可见风险与真实观察，不伪造 `PASS`，也不在调用前禁止任务**：任务权限、锁、依赖与特定安全 / 独立身份条件满足且宿主工具存在时，仍允许实际尝试 T1 / T2 / T3；T0 若涉及产品实现，仍须 Master 明确例外授权。只有工具 / 实例**客观已知不存在**、本任务**实际派发调用已经失败** / 句柄失效 / 结果为空 / 超时 / 无法核对，或上述治理前置不满足时，才不得推进依赖该结果的状态，如实报告失败 / 未完成或交接。不得伪造成功、句柄或终局分类。
7. **Minimum viable context**：主对话仅保留决策所需上下文；独立任务交付必须保留可复核的原始证据引用、限制及未验证假设，避免摘要代替事实。
8. **Warning is not waiver**：能力风险告警只影响「能否声称具备该能力」与风险记账；既不把未探测当可用，也不把未探测当禁止尝试。告警不放宽权限、敏感数据授权、路径 / 资源锁、依赖、角色职责、可信 Reviewer 身份或 G1–G6；这些治理证据缺失时仍按原门禁失败处理。

> **现行契约优先：** 上述原则 6 与 8 中「未探测不禁止尝试」的表述是 #174 方向的提案，不是当前规则；现行 C1–C4 硬门禁仍按 `kit/orchestration.md` 执行。冲突与建议见 §2.6 C-1。

**Role 与 Instance 的关系（冻结，三点）：**

1. `Role ≠ Instance`，Role 也不是固定常驻实例、固定进程数或固定模型数。
2. 允许：同一职责由不同实例承担；同一实例在不同任务 / 阶段被明确授权承担不同职责。
3. 禁止：按 Role 预建常驻岗位实例并要求所有任务在它们之间交接；用执行过该任务的同一实例或同一上下文充当独立 Reviewer；把「三个治理角色」理解成「必须常驻三个模型会话」。主 Agent 作为当前会话的 Master 入口是正常形态，不构成「Role 常驻实例」反例。

### 2.2 决策顺序与「选择不是派发」

冻结顺序（不得倒置）：

1. **Task**：先形成可验收的任务契约（目标、AC、依赖、允许 / 禁改路径、资源、风险、证据要求）。任务不成立或依赖 / 锁不满足时，停在任务层。
2. **Topology**：基于 Task 的性质（确定性步骤、隔离需求、并行可能性、独立审查要求、风险与不可逆性）选择执行结构候选；此步只产出建议与排除原因。
3. **Role / Model matching**：在选定拓扑内，用现有角色选择入口与 S1–S5 匹配职责、候选实例与模型；不得先按角色名册或模型排名反推任务和拓扑。
4. **Authorized dispatch**：只有取得活动任务锁、状态推进到 `DISPATCHED` 且任务包交给真实执行实例并被确认接收后，才算派发；现行 C1–C4 与 G1–G6 仍按 `kit/orchestration.md` 执行。
5. **Evidence & review**：真实结果、当前 head 证据、独立审查与 Master 批准；本步不因前四步的建议而自动通过。

| 阶段 | 典型产物 | 是否推进任务状态 | 不能声称什么 |
|---|---|---|---|
| 发现 / discovery | 候选实例、模型、能力记录 | 否 | 已选型、已授权、已启动 |
| 选择 / selection | `selected_topology`、`role_assignments`、`selection_status: RECOMMENDED / UNKNOWN / BLOCKED / MANUAL_HANDOFF` | 否 | 已派发、已执行、已通过审查 |
| 派发 / dispatch | 锁、`DISPATCHED` 记录、真实实例接收与可寻址句柄 | 是，且仅在真实接收后 | 已成功完成、已验收 |
| 执行结果 / result | wait / collect 返回的状态、产物、命令输出、退出码、head SHA | 仅在结果可核对时 | 未返回或空结果算成功 |

**选择不是派发。** 推荐拓扑、角色匹配报告、模型评分、候选排序、`RECOMMENDED` 状态都只是决策输入：它们不取得锁、不改变状态、不扩大允许路径、不创建实例、不证明审查已发生。反过来，收到选择报告也不使执行者成为「已派发」，更不允许其自称已启动其他 Agent 或已完成独立审查。

### 2.6 冲突登记与建议

## 3. 决策算法

> 本节至 §10 是 Stage B–E 的设计提案，不属于 #177 冻结范围；与 §2 冲突时，以 §2 的定义和现行契约为准。

### 3.1 输入

读取任务源的目标、AC、依赖、路径、资源锁、验收证据及风险/不可逆动作；Runtime 实际能力事实；项目的硬性人工决策规则；执行上下文估算；当前 scope 中**可靠**的历史表现（足够样本且身份/任务类型一致）。不读取其他 scope 的私有报告，不从聊天文本生成权限。

### 3.2 必要的独立性判断

先判定是否需要：
- 独立判断（例如安全、权限、破坏性变更、高风险复杂重构、具有实质不确定性的结论）；
- 上下文隔离（长日志、大型仓库、大量文档，主 Agent 不应装载全部材料）；
- 并行探索（任务依赖与路径、资源锁允许；不同探索结果可独立验证）；
- 工具/权限隔离（专门账号、网络、文件或写入能力必须隔离）。

即便不满足以上条件，也要执行现有 Master 独立检查/审批契约；任何免除独立 Reviewer 的方案不能默默降低 Master 独立检查。Master 本人执行实现时，既有例外授权规则和不自批约束照旧；若真实独立审批者不可用，则保持阻塞或人工交接，不将同一上下文的自评标记为独立审核通过。

### 3.3 拓扑候选

- **T0 — Tool/Skill in main loop**：确定性步骤、简单查询或无隔离需求；Skill 仅帮助正确调用 Tool。若涉及实现文件变更，仍必须遵守现有 Master 默认不实现、显式例外授权与后续门禁。
- **T1 — Sequential execution**：任务由一个真实 Execution 实例完成，再由 Master 在独立检查阶段验收；不是“执行者自批”。
- **T2 — Execution + independent Reviewer**：风险、审查策略或专业独立判断明确要求时启用，并由 Master 决策。
- **T3 — Parallel isolated executions**：存在多个可独立验收的子任务、依赖为 DAG、路径/资源冲突检查通过时启用；必要时可附加独立 Reviewer。
- **T4 — External/Manual handoff**：任务客观要求隔离执行、独立身份或专用工具（例如敏感数据、需要可信独立 Reviewer、宿主未提供的权限），而运行时无法真实提供；或工具 / 实例客观已知不存在；或本任务实际调用已经失败且无法在可执行路径内恢复时，输出明确可执行任务包，交人工开启隔离会话。**单纯的能力探测缺失、未执行、`UNKNOWN`、`STALE`，或未证明工具客观不存在的探针失败，不触发表 T4，也不得据此排除 T1–T3**：记录风险与真实观察后，在权限 / 锁 / 依赖 / 独立条件满足且宿主工具存在时，仍可实际尝试。不能伪造 spawn、句柄或结果。

以上并非强制使用固定数目的角色实例，也不创建 Backend/Frontend/Database 等岗位代理；一个任务的独立 Reviewer 由其独立审查需求定义。

### 3.4 选择流程与不变量

本流程顺序固定为 **Task → Topology → 角色 / 模型匹配**；不得先按角色名册或模型排名反推任务与拓扑。以下「候选」「推荐」都不是派发。

1. 完成任务契约与风险分级（无法判定的高影响事项升级人工决定，不自动判低风险）。
2. 生成候选 T0–T4，并区分**治理硬过滤**与**探测风险标记**：
   - 治理硬过滤只淘汰真正违反治理不变量或客观不可执行的候选：权限 / 敏感数据授权、任务要求的可信 Reviewer 身份与独立性、路径 / 资源锁与依赖、无权限扩张；以及「该候选所依赖的工具 / 实例**客观已知不存在**」或「本任务对该候选的**实际调用已经失败且无法恢复**」。
   - 能力探测缺失、未执行、`UNKNOWN`、`STALE`，或未证明宿主工具客观不存在的探针 `FAIL`，**不淘汰候选，也不强制降级为 T0 或转人工**：给候选附加风险 / 未验证标记；权限、锁、依赖与任务特定安全 / 独立身份条件满足且宿主工具存在时，仍允许实际尝试 T1 / T2 / T3。不得把「未探测」当作「可用」或「已证明隔离 / 终局可分类」，也不得把「未探测」当作「禁止尝试」。T0 若涉及产品实现，仍须 Master 明确例外授权，不能为绕开探测而强制选择 T0。
3. 对可执行候选比较预估任务完成率、严重缺陷风险、总体成本与延迟；缺样本标记 UNKNOWN，不伪造精度。
4. 输出结构化推荐与备选、排除原因、实际证据来源/时间、风险、人工决策点。
5. 只有真正取得锁、状态推进且真实执行实例确认接收后才记 DISPATCHED；推荐和调度尝试不算执行成功。
6. 审查、Master 批准与合并后验证不变。若目标漂移或关键不变量失败，回滚或停止，不以成本优势补偿质量退化。

**禁止**在没有正式变更 AGENTS.md 和核心契约、验证矩阵前引入“轻量模式可自批/可自行合并”的例外；本阶段仅优化执行实例拓扑，不缩减治理门禁。

### 3.5 探测状态、实际派发结果与治理条件的判定

必须区分三类互相不能替代的事实：

1. **探测状态**：探针是否运行、结论是 `PASS` / `FAIL` / `UNKNOWN` / `STALE`。它只描述「是否已观察到该能力」，不证明本任务结果，也不自动授予或禁止尝试。
2. **本任务实际派发结果**：本次调用是否真的发生，是否返回可核对的句柄、状态与产物。它决定依赖该结果的状态能否推进。
3. **治理前置**：任务权限、敏感数据授权、允许路径、路径 / 资源锁、依赖、角色职责与不自批、任务特定隔离要求、独立 Reviewer 可信身份、G1–G6。它们各自需要有效证据，不能用探测告警替代。

下表是本提案对未来行为的统一口径；它**不改变现行 `kit/orchestration.md`**，正式落地须由 #174 后续契约任务完成。

| # | 情形 | 允许 / 应做的处理 | 禁止的写法或做法 |
|---|---|---|---|
| 1 | 宿主工具存在，但探测未运行 | 允许在权限 / 锁 / 依赖 / 独立条件满足时**实际尝试** T1 / T2 / T3；显示「未探测」风险并记录时间与限制 | 因未探测排除候选、强制 T0 或转人工；把未探测写成 `PASS` |
| 2 | 宿主工具存在，探测为 `UNKNOWN` / `STALE` | 同上；标记证据未知或过期，真实尝试结果照常取证 | 把未知 / 过期当已验证；据此禁止实际尝试 |
| 3 | 探针 `FAIL`，但未证明宿主工具客观不存在（例如探针设计、环境或权限问题） | 如实记录 `FAIL` 与原因，区分「探针失败」与「产品能力失败」；治理条件满足时仍可实际尝试 | 把 probe `FAIL` 直接等同于本任务调用失败；用 probe `FAIL` 全局禁止候选 |
| 4 | 工具 / 实例**客观已知不存在** | 不发起假装调用；报告「不可执行 / 未完成」，需要时走 T4 人工交接 | 伪造 spawn、句柄、状态或成功结果 |
| 5 | 本任务实际派发调用**已发生且失败** | 记录实际失败 / 未完成；停止依赖该结果的状态推进；必要时交接 | 用探测告警掩盖实际失败；记成成功 |
| 6 | 本任务调用返回空结果、超时、句柄失效或结果无法核对 | 视为失败 / 未完成；不得推进依赖该结果的状态 | 把空结果、超时或无法核对当作成功或稳定终局 |
| 7 | 探测 `PASS`，但本任务调用仍失败 | 按实际失败处理；探测 `PASS` 不保证单次任务结果 | 用探测 `PASS` 抵消实际失败 |
| 8 | 敏感数据 / 任务特定隔离要求 / 需要独立审查但 Reviewer 可信身份缺证据 | 按该任务的独立条件阻断、补证或交接；身份未知不得当作独立审查通过 | 用 C1–C4 告警或「已尝试 T1–T3」替代隔离 / 身份证据 |
| 9 | C2 未知 | 不证明上下文隔离；任务确需隔离时须补独立证据，否则记录风险后可尝试 | 声称已隔离或已满足 C2 |
| 10 | C4 未知 | 不证明成功 / 失败 / 取消可区分；实际结果仍须可核对 | 把未知、空结果或无法核对当作成功 |
| 11 | T0 涉及产品实现但无 Master 明确例外授权 | 不得以 T0 实现产品文件 | 为绕开探测而强制选择 T0 |

**结论：** 探测状态决定「能否声称已验证」与风险记账；本任务实际调用结果决定「能否推进状态」；治理前置决定「是否允许尝试」。三者不得互相替代，也不得用告警豁免权限、锁、依赖、身份或 G1–G6。

## 4. 输出契约和可审计证据

- `candidate_topologies[]`: `id`、`eligible`、`hard_constraint_results[]`、`tradeoffs`

隐私：本地模型候选与性能记录仍按 `.local/agent-orch/<scope-id>/` 管理，绝不将敏感候选/运行环境细节复制进公开 Issue/PR。公开任务载体仅记录非敏感的拓扑决策摘要、证据索引与最终真实派发状态。严禁记录密钥及私人路径。

## 5. 评测设计：目标实现而非角色表演

基准分层：文档/配置小任务、跨模块功能、独立并行任务、安全权限/不可逆变更、工具/身份故障与审查对抗样例。每类不少于若干人工审核的真实验收用例；先锁定评价标准，再运行对照，不能只挑有利案例。

硬性验收：越权写入=0、自批冒充独立审查=0、非法锁/依赖绕过=0、未经许可不可逆操作=0、证据伪造=0、关键回归未检测=0。若任何关键硬门禁失败，不允许用成本改善抵消。

量化指标：端到端 AC 通过率、任务实际 VERIFIED 率（附样本及滞后窗口）、首次验收率、修复轮次、后续回归缺陷严重度、Reviewer 真实缺陷发现/误报/漏报、累计模型 Token（包含子代理）、运行耗时、实际/估算成本、跨 Agent handoff 数及不必要上下文载入量。没有真实记录则标 UNKNOWN，不得把估算当成实际。

比较法：在相同任务集与测试环境下做 T1/T2/T3 对照；按任务类别分层并多次重复；包含完整链路回归与相邻任务回归；保留失败轨迹。仅在质量硬约束均满足且端到端目标达成结果不显著退化时才考虑以成本优势折叠子代理。样本不足则建议继续收集，不改变默认行为。

## 6. 兼容、可靠性与回滚

- 默认 **observe-only**：记录候选及决策，不真正启动 Agent、不改变角色权责、锁与状态，且默认沿用现有派发路径。
- 后续受控试点须显式 opt-in。试点期间，能力探测缺失、未执行、`UNKNOWN`、`STALE`，或未证明工具客观不存在的探针 `FAIL` 只产生可见风险提示与真实观察记录；权限、锁、依赖与任务特定安全 / 独立身份条件满足且宿主工具存在时，仍允许实际尝试 T1 / T2 / T3，**不因探测状态默认停止正常作业、排除候选或强制转 T0 / 人工**。工具 / 实例客观不存在、本任务实际调用失败 / 句柄失效 / 结果为空 / 超时 / 无法核对，或上述治理前置不满足时，才停止依赖该结果的动作并如实转人工或保持未完成。
- 不能由实验拓扑动态修改 `AGENTS.md`、项目权限、角色模型或配置；所有重大变更另经 owner 授权。
- 任务调度前后保留可回退到原角色选择/派发流程的开关；旧记录可读、新字段可选，确保 local/github 双底座一致。
- AgentOrch 仍不是 Runtime。实现 CLI 应保持 Python 标准库零第三方依赖；不将 Anthropic 参考 loop.py 直接植入产品。
- 固定流程优先确定性代码，规则限制下沉到执行工具与宿主审批层；Skill 不能替代技术强制约束。

## 7. 分阶段实施路线与 Issue 边界

### Stage A — 原则与契约冻结（串行）

- 明确治理角色 ≠ Agent 实例；Task/Context/Topology 概念与决策顺序。**该定义子项由 #177 以 §2 交付；#177 只冻结定义，不完成 Stage A 整体。**
- 对 `docs/PLAN.md`、`AGENTS.md`、`kit/orchestration.md`、现有阶段计划先进行差异分析，避免重复权威。核心角色权限或状态变更须独立批准；本阶段不改变权限。
- 审核旧文件迁移相关 Issue 的预期路径，以免在迁移期间编辑两个等价入口。
- DoD：一份唯一权威的新增决策契约；双底座与 Reviewer 独立性不变量测试通过。**该 DoD 尚未因 #177 全部满足：不变量测试与 Stage B–E 仍待后续任务；不得把 #177 的合并当作 Stage A 完成或 T0–T4 已批准。**

### Stage B — 任务分类与拓扑推荐（依赖 A）

- 实现 Task Risk/Context/Independence classifier 与候选 T0–T4；任务类型从任务源提取。
- 实现“先判断是否值得独立 Agent，再调用 S2/S3/S4 模型匹配”。
- 无权限、依赖或锁冲突、工具 / 实例客观不存在时输出 `BLOCKED` / `MANUAL_HANDOFF`；能力未验证 / 无证据时输出带风险告警的候选与备选并标记未验证，**不得因探测状态排除 T1–T3 候选或强制 T0**。分类器只负责推荐；是否实际尝试由后续派发在治理条件满足且宿主工具存在时决定。确保推荐绝非派发。
- DoD：单元测试覆盖普通/高风险/歧义、缺身份、资源冲突、禁止自批及模式选取。

### Stage C — Runtime Adapter 接线（依赖 B）

- 在已存在的运行时发现与工具事实基础上只增加拓扑建议映射；适配 OpenCode/Codex/DSH 要以各自可信能力实测为依据。
- 实际 spawn/wait/collect 只有在真实调用返回可核对结果时才记成功；工具 / 实例客观不存在时报告不可执行，本任务实际调用失败、句柄失效、结果为空、超时或无法核对时如实记失败 / 未完成并停止依赖该结果的状态推进。探测未跑 / `UNKNOWN` / `STALE` 或未证明客观缺失的探针失败只记风险，不阻止在治理条件满足时实际尝试。
- DoD：模拟 adapter + 至少一种经授权实际运行环境的完整交付证据；工具 / 实例客观不存在或实际调用失败时如实报告不可执行 / 失败，不伪造成功。

### Stage D — 端到端评测和反馈（可与 C 的文档子项并行）

- 复用已有 S4/ETR/评价可信度工作，不另起一套总分；新增端到端目标完成和拓扑消耗归因。
- 构造包含“折叠后邻接任务受损”“独立性绕过”“风险错误降级”的负向对照。
- DoD：基线、比较工具、原始轨迹、覆盖率/样本数、失效回退和审查记录可重现。

### Stage E — 有门禁的试点、发行、文档同步（依赖 C 与 D）

- 默认关闭自动改变拓扑，仅以建议模式覆盖现有工作流；有证据后 opt-in 试点。
- 下游项目旧布局与 DSH 发行包沿用独立既有 Issue，不重复创建并行发行体系。
- DoD：local/github，Windows/Linux，模拟/真实环境边界、发行扫描、回滚、负向安全测试通过；主分支按当前 head 合并后复测。

## 8. 应避免的反模式

- 为 Backend、Database、Security 等岗位永久创建代理，迫使每个任务全链路交接。
- 仅因为三种治理角色存在便默认启动三份模型会话。
- 因任务简单就把“执行者自审”写成独立审核，或取消 Master 的审批责任。
- 把 Prompt 内的安全要求误当强制执行；把同 family alias 或自报底层 ID 当可信独立模型。
- 以 Issue 全关闭、Token 降低或模型自评替代用户目标的真实验收。
- 在无真实样本时引入虚假的“最优拓扑打分”。

## 9. 与现有工作去重

此方案在既有 **角色发现/匹配 S1–S5** 前引入 Task → Topology 的上游判定；重用 ETR 和真实表现记录。**ETR 不在本文另立口径**：字段、公式、覆盖率、冷启动、数据缺失与阈值语义的唯一权威是 `docs/design/next-phase-governance-and-agent-performance.md` §7.1–7.3；`docs/implementation-plan.md` §14.3 只登记阶段约束并引用该设计，不定义字段、权重或 tie-break，不构成第二套权威。本文不新增字段、权重或 tie-break，也不复述。独立 Reviewer 的可信底层模型身份与 alias 映射仍由 #170 等已有专门工作负责；#170 的 `agent-registry.md` 规范身份口径是本文件唯一接受的独立性判据，本文不放宽、不新增 alias / family / 实例自述例外，也不声称已验证任何模型身份、隔离或 DSH runtime。DSH 的 `ao_master`、`ao_execution`、`ao_reviewer` 名称保持不变，它们表示治理职责入口而不是岗位常驻 Agent。旧项目 `agentorch/` 接入、发行包、文档迁移沿用现有 Issue，不复制实现工作；本文不新增任务依赖。

## 10. 交付顺序与停止条件

A 冻结定义（#177 交付 §2；Stage A 整体 DoD 与不变量测试仍未完成）→ B 只读推荐 → C 受控 Runtime 接线 → D 客观评测 → E 试点发行。A/B 可先在 `observe-only` 完成；C 与 D 可在接口冻结后按独立文件/任务并行。任一关键治理门禁失败、任务要求独立审查但无可靠 Reviewer 独立性依据、状态 / 锁不一致、证据不足、工具 / 实例客观不存在或本任务实际调用失败，均停止推广新拓扑并恢复既有路径；**单纯的能力探测缺失 / `UNKNOWN` / `STALE`，或未证明客观缺失的 probe `FAIL`，只记风险，不阻止在治理条件满足且宿主工具存在时实际尝试 T1–T3，也不作为停止正常项目作业的理由**。

**验收最终判据**：一个项目能够解释“为何此任务使用 Tool/Skill、单执行 Agent 或并行/独立审查 Agent”，能给出真实证据和替代方案，并在质量和权限不退化前提下证明端到端目标达成率或效率得到改善。
