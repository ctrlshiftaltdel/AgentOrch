# AgentOrch 主动式 SemVer 发行节奏与版本治理（提案）

> 日期：2026-10-28；状态：**分类规则、批次边界口径与常设授权边界已由 #192 冻结**；其余仍为 PROPOSED / NOT IMPLEMENTED。此文档为专项设计，不替代 `docs/PLAN.md`、`docs/implementation-plan.md`、`release/README.md` 或现行 G1–G6 门禁；合并后可执行口径以 `release/README.md` 第 5.3 节为准。**#192 的冻结只是规则冻结，不是发版授权**：常设自动发版授权范围为空，在 Owner 另一次明确授权之前不得打 tag 或创建 Release。契约、构建及升级器修改合并之前，维持原有发布授权规则。

## 1. 用户目标与触发规则（#192 冻结）

> 冻结状态：本节的三档分类与判定规则由 #192 冻结，后续发行任务按此口径分类。文字冻结**不等于**授权发版——常设授权范围见第 2 节，当前为空。

Master 在日常任务推进中主动管理版本，不以用户每次说“发布”为必要条件。以最新**已发布** tag（`git tag --sort=-v:refname` 的第一个）为基准，而不是以 `VERSION.md` 或聊天记忆为基准，按对外兼容性而非代码行数选择 SemVer：

| 类别 | 兼容性规则 | 例（基于 v1.7.0） |
|---|---|---|
| PATCH | 修复错误、测试/文档/兼容性修正，公开行为不产生不兼容变化 | v1.7.1 |
| MINOR | 向后兼容的新能力或对外行为扩展 | v1.8.0 |
| MAJOR | 破坏性 API/套件入口、配置、数据/格式、授权语义或升级路径变化 | v2.0.0 |

判定规则：

- 分类只看**对外兼容性**：重构是否 MAJOR 取决于是否改变对外兼容性，仅重大工程量不自动升级主版本。涉及安全的严重缺陷可以立即发 PATCH（若不兼容则按 MAJOR 并披露），普通零散修复可以按稳定批次合并。
- **混合变更取最大 bump**：一次发行包含多类改动时取 MAJOR > MINOR > PATCH 中的最高一级，不得拆成多次低级别发行来规避等级。
- **空发布不允许**：自最新已发布 tag 以来没有已合并且已验证、用户可感知的变更时不得发版，不得为“走流程”创建空 Release。
- **版本相对最新已发布 tag 计算**：候选版本号以该 tag 为准递增。若该 tag 与 `VERSION.md` 的 `Release version:` 记录不一致（tag 领先、落后或缺失），**停止发行并核对**，不得按任一来源擅自推定、重打或改名历史 tag。

## 2. 主动发行节奏与控制

> 冻结状态：批次边界的判定口径（按实际用户可用成果与高风险门禁，不按 PR 数量）与常设授权边界由 #192 冻结；本节出现的数量、天数等数值只是建议默认值，不是门禁，也不是授权。

- Master 每次恢复会话、重要 PR 合并后、阶段完成时执行只读发行评估：检查上一个发布之后的已合并已验证 Issues/PR、兼容性标签、CHANGELOG 候选、积压、失败/回滚与未发布提交。不得从聊天记忆猜事实。只读表示**不改 `VERSION.md`、不打 tag、不建 Release、不上传资产**；离线或没有 GitHub / 构建权限时只产出报告并标 `NOT_RUN` / `BLOCKED`，不得声明已发布。
- PATCH 触发：已经积累若干独立已验证的修复（建议默认 2–5 项），或者有经确认的紧急 bug/security 修复；无实际变更不发行。积压达到合理窗口（建议 7 天，可配置）时主动提出发行；不因没有达到数量而无限推迟。
- MINOR 触发：至少一个完整、已验证且可交付的向后兼容功能组完成，相关依赖闭合。不要把未完成的实验功能包装进 Release。
- MAJOR 触发：破坏兼容性设计、迁移/升级测试、回退文档及必要人工决策均完成，才能发行。
- 批次边界以实际用户可用成果和高风险门禁为准，而不是每个 PR 必发；若同时有多种改动，以最高级别 bump。
- “主动”指**在 Master 实际运行且具备 GitHub/构建权限时**不必等待用户另行发起发布请求；不声称 AgentOrch 是常驻后台服务。无人运行时，若要求无人工在线也定期发行，则需另建 CI scheduler/受控自动化并明确账户、权限、安全策略。
- **常设自动发版授权范围（#192 冻结：空集）**：Owner 已表达的“无需逐次要求”是一种意图，不折算为授权。当前没有任何 PATCH / MINOR 处于“无需逐次确认即可发版”的常设范围内；没有 Owner 另一次明确授权（写明批次、版本级别与范围），**不得打 tag 或创建 Release**。MAJOR、破坏性迁移、无法回退或安全授权变化仍须单独提交 Owner 决策。该冻结只确定规则与边界，不批准自动发版，也不创建任何 tag / Release。
- 创建发布任务仍遵守任务登记、路径锁、Master 独立审查、合并后验证、真实 GitHub Release/资产上传及事后核验，不得允许 Execution 自发发版。

## 3. 关键兼容问题：Release version 与 Format version

目前 `VERSION.md` 分别记录 `Release version: 1.7.0` 与 `Format version: 1.7`；`release/README.md` 说明 `scripts/update_agentorch/versions.py` 的 `tag_matches_format()` 要求 tag 的 major.minor 与 format_version 相等。此旧约束会导致“Release 1.8.0 但 Format 仍为 1.7”的正常兼容功能发行被升级器拒绝。

必须先实施以下解耦，才可按本方案发行不同步的 MINOR。本节只描述约束，不修改升级器；分类与授权边界冻结归 #192（阶段 A），实现与测试归 #193（阶段 B）。**截至 #192，这一耦合仍然存在**：`tag_matches_format()` 仍要求 tag 的 major.minor 等于 `format_version`，所以“Release 1.8.0 + Format 1.7”的发行在当前实现下仍会被升级器拒绝；#192 不修改 `scripts/update_agentorch/`，也不声称已解耦。
1. SemVer 只代表对外发行版本；格式号独立表示存储/清单/升级契约，需要变化时才升级。
2. 更新器验证**可信版本来源 + manifest 格式支持矩阵/迁移路径**，不再以 tag 前两段相等作为通用必要条件；在过渡期允许旧包合法规则，新的 release 元数据注明 format，未知或不支持格式失败关闭。
3. 仅签名/哈希/Tag/包一致性、反回滚约束及 Format compatibility 决定来源可接受性，不得用“忽略错误”绕过旧 `VERSION_MATCH`。
4. 配套更新真实升级 fixture、正负用例、`docs/upgrade.md`、`release/README.md`、MANIFEST 消费端和版本解析器。确认旧版本到新版本、跨格式兼容、错误版本、不存在迁移路径时的失败行为。
5. 正式命名统一 `vMAJOR.MINOR.PATCH`，保留历史 tag 和资产，旧 `1.6` 等不可变更。

## 4. Release Candidate / 发布流水线

**计划**：对已合并且 VERIFIED 的任务生成本轮 release manifest（Issue/PR、变更类型、用户可感知结果、风险、兼容性、升级要求）；检测版本冲突、tag 是否存在、是否跳版本、是否遗漏支持的发行包。

**准备**：从最新 main 做独立发布任务；更新版本/变更说明、构建正式名称资产；执行发布规定的完整单测、合成场景、包内自检、四档 CI（Linux 3.12 / 3.13、macOS、Windows）、真实可复现性与隐私检查。验证各资产安装/兼容性；DSH 阶段完成后同时包含 Kit zip 和 `-dsh.tgz`，两者使用相同 tag/版本。

**审批**：Master 查验当前 HEAD 证据与 G1–G6；常设授权范围当前为空（#192 冻结），因此**不存在**可直接执行的常规 PATCH/MINOR 范围，每次发行仍需 Owner 明确授权。MAJOR、需人工决策的迁移与安全事件仍停下获得明确批准。

**发布**：在获得该次明确授权后，由 Master 或受控发行执行器在合并后的 main 上创建唯一不可变 tag、Release、全部资产和 SHA256；先核对现有 tag/release 防重复，部分失败时记录状态并恢复，不双发，不覆盖旧资产。

**收口**：下载并复核真实发布资产、校验 tag→SHA、Release notes、发布后升级冒烟；写回发行任务、关联 Issues/PR、主阶段计划状态。失败则标记阻塞/恢复策略，不能宣称 RELEASED。

## 7. 明确非目标和失败准则

不为形式而发空版本、不把每个 commit 自动发布、不承诺无人运行时持续后台执行、不允许自动绕过人工授权、测试 G 门或审查独立性、不根据文件数量决定版本、不把 Format 与 Release 强行同步。不允许发布资产与 tag 不一致、不允许把尚未完成的 DSH 功能写成已发布。缺可信 API、CI、权限、版本或人工决定时只能 STOP/NEEDS_HUMAN_DECISION。

**当前状态（#192）**：分类规则、批次边界口径与授权边界已冻结；常设自动发版授权范围为空，**自动发版未启用**，本稿与本次冻结都不创建任何 tag / Release。

正式启用条件：相关设计文稿审查合并、Owner 常设授权确认、兼容性改动经过负向/旧版升级测试、双底座核验与真实发布过程验收。上述条件未全部满足前，只能按空授权处理。
