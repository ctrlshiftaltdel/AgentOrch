# AgentOrch 主动式 SemVer 发行节奏与版本治理（提案）

> 日期：2026-10-28；状态：PROPOSED / NOT IMPLEMENTED。此文档为专项设计，不替代 `docs/PLAN.md`、`docs/implementation-plan.md`、`release/README.md` 或现行 G1–G6 门禁。契约、构建及升级器修改合并之前，维持原有发布授权规则。

## 1. 用户目标与触发规则

Master 在日常任务推进中主动管理版本，不以用户每次说“发布”为必要条件。以最近已发布的正式版本为起点，按照兼容性而非代码行数选择 SemVer：

| 类别 | 兼容性规则 | 例（基于 v1.7.0） |
|---|---|---|
| PATCH | 修复错误、测试/文档/兼容性修正，公开行为不产生不兼容变化 | v1.7.1 |
| MINOR | 向后兼容的新能力或对外行为扩展 | v1.8.0 |
| MAJOR | 破坏性 API/套件入口、配置、数据/格式、授权语义或升级路径变化 | v2.0.0 |

重构是否 MAJOR 取决于对外兼容性；仅重大工程量不自动升级主版本。涉及安全的严重缺陷可以立即发 PATCH（若不兼容则按 MAJOR 并披露），普通零散修复可以按稳定批次合并。多个改动取最大 bump，且版本号相对最新**已发布** tag 计算；与当前 VERSION.md 记录不一致时停止并核对。

## 2. 主动发行节奏与控制

- Master 每次恢复会话、验收重要 PR、阶段完成时执行只读发行评估：检查上一个发布之后的已合并已验证 Issues/PR、兼容性标签、CHANGELOG 候选、积压、失败/回滚与未发布提交。不得从聊天记忆猜事实。
- PATCH 触发：已经积累若干独立已验证的修复（建议默认 2–5 项），或者有经确认的紧急 bug/security 修复；无实际变更不发行。积压达到合理窗口（建议 7 天，可配置）时主动提出发行；不因没有达到数量而无限推迟。
- MINOR 触发：至少一个完整、已验证且可交付的向后兼容功能组完成，相关依赖闭合。不要把未完成的实验功能包装进 Release。
- MAJOR 触发：破坏兼容性设计、迁移/升级测试、回退文档及必要人工决策均完成，才能发行。
- 批次边界以实际用户可用成果和高风险门禁为准，而不是每个 PR 必发；若同时有多种改动，以最高级别 bump。
- “主动”指**在 Master 实际运行且具备 GitHub/构建权限时**不必等待用户另行发起发布请求；不声称 AgentOrch 是常驻后台服务。无人运行时，若要求无人工在线也定期发行，则需另建 CI scheduler/受控自动化并明确账户、权限、安全策略。
- 为满足 Owner 已表达的“无需逐次要求”，本提案**建议**的常设授权范围如下（**尚未生效**）：在质量门全绿、无未决人工决策、版本兼容和已授权范围内，Master 可执行常规 PATCH/MINOR 的打 tag/Release 流程；MAJOR、破坏性迁移、无法回退/安全授权变化仍必须单独提交 Owner 决策。该范围须由 #192 冻结、经 Owner 确认并完成契约更新后才生效。**本设计提案本身不改变当前发布权限，也不自行创建任何 tag / Release。**
- 创建发布任务仍遵守任务登记、路径锁、Master 独立审查、合并后验证、真实 GitHub Release/资产上传及事后核验，不得允许 Execution 自发发版。

## 3. 关键兼容问题：Release version 与 Format version

目前 `VERSION.md` 分别记录 `Release version: 1.7.0` 与 `Format version: 1.7`；`release/README.md` 说明 `scripts/update_agentorch/versions.py` 的 `tag_matches_format()` 要求 tag 的 major.minor 与 format_version 相等。此旧约束会导致“Release 1.8.0 但 Format 仍为 1.7”的正常兼容功能发行被升级器拒绝。

必须先实施以下解耦，才可按本方案发行不同步的 MINOR。本节只描述约束，不修改升级器；分类与授权边界冻结归 #192（阶段 A），实现与测试归 #193（阶段 B）：
1. SemVer 只代表对外发行版本；格式号独立表示存储/清单/升级契约，需要变化时才升级。
2. 更新器验证**可信版本来源 + manifest 格式支持矩阵/迁移路径**，不再以 tag 前两段相等作为通用必要条件；在过渡期允许旧包合法规则，新的 release 元数据注明 format，未知或不支持格式失败关闭。
3. 仅签名/哈希/Tag/包一致性、反回滚约束及 Format compatibility 决定来源可接受性，不得用“忽略错误”绕过旧 `VERSION_MATCH`。
4. 配套更新真实升级 fixture、正负用例、`docs/upgrade.md`、`release/README.md`、MANIFEST 消费端和版本解析器。确认旧版本到新版本、跨格式兼容、错误版本、不存在迁移路径时的失败行为。
5. 正式命名统一 `vMAJOR.MINOR.PATCH`，保留历史 tag 和资产，旧 `1.6` 等不可变更。

## 4. Release Candidate / 发布流水线

**计划**：对已合并且 VERIFIED 的任务生成本轮 release manifest（Issue/PR、变更类型、用户可感知结果、风险、兼容性、升级要求）；检测版本冲突、tag 是否存在、是否跳版本、是否遗漏支持的发行包。

**准备**：从最新 main 做独立发布任务；更新版本/变更说明、构建正式名称资产；执行发布规定的完整单测、合成场景、包内自检、四档 CI（Linux 3.12 / 3.13、macOS、Windows）、真实可复现性与隐私检查。验证各资产安装/兼容性；DSH 阶段完成后同时包含 Kit zip 和 `-dsh.tgz`，两者使用相同 tag/版本。

**审批**：Master 查验当前 HEAD 证据与 G1–G6；只在已授权的 PATCH/MINOR 常规发行范围内执行。MAJOR、需人工决策的迁移与安全事件仍停下获得明确批准。

**发布**：由 Master 或受控发行执行器在合并后的 main 上创建唯一不可变 tag、Release、全部资产和 SHA256；先核对现有 tag/release 防重复，部分失败时记录状态并恢复，不双发，不覆盖旧资产。

**收口**：下载并复核真实发布资产、校验 tag→SHA、Release notes、发布后升级冒烟；写回发行任务、关联 Issues/PR、主阶段计划状态。失败则标记阻塞/恢复策略，不能宣称 RELEASED。

## 5. 与 AVE、架构与发行计划协调

- 自适应验证 Epic #184：开发与 PR 可按未来风险分级，但**正式发行始终完整验证**，不允许因优化测试而缩减正式发行级门禁。
- AVE 的风险驱动合并门试点 #188：需要**单独 Owner 授权**，本提案不授予该授权，也不降低现行 G1–G6 或发行级完整验证。
- Reviewer 可信身份 #170：底层模型身份与显式别名映射修复完成前，Reviewer 独立性与模型身份判定保持未实证（`UNKNOWN`），不能作为发行证据。
- 任务驱动拓扑 #176：角色/运行时推荐不能代替 Master 发行责任或 Owner 决策；运行时能力不足就写明人工交接。
- 项目结构治理 #146/#150/#151：版本策略唯一权威归 `release/README.md`（合并后）；设计稿仅作提案，`docs/implementation-plan.md` 仅管理实施阶段，避免重复规则。迁移核心契约时协调路径。
- DSH #161–#167：完成前只发行已实现资产，完成后两发行包同版本同 Release；任何 DSH bundle 失败均阻断对应 Release，而不是悄悄缺失。DSH 运行时未实证，只能按实机 / CI 实际状态表述，不得写成已验证或已发布。
- 自我完善/更新引擎：发行记录和兼容性源数据可被更新机制读取，不能由无证据的 Agent 自评决定版本等级。
- local/github：核心版本选择一致；没有 GitHub 连接的 local 环境只能生成经过验证的本地发行候选并提示交接，不假装已发布 GitHub Release。

## 6. 可落地实施阶段与验收

### A — 契约冻结和版本兼容审计（#192）
检查现行发布制度、版本解析器、格式耦合、DSH、升级器、已有测试；冻结 SemVer、触发策略、批次边界、常设授权范围与例外；Owner 审定。提供版本决策表及可审查测试矩阵。

### B — 版本解耦与升级器安全兼容（#193）
实现 Release/Format 分离、受控兼容矩阵、正式三段版本验证及旧包迁移；验证旧 tag 不受损、新 minor 不升 Format 仍可升级、安全错误失败关闭。

### C — 主动式发行规划与记录（#194）
只读 release readiness/report 命令或可移植提示词，扫描已 VERIFIED 的合并项自动分组/推荐版本/创建发行任务；避免虚构后台持久在线、绕过 owner 和无证据 auto-pass。默认 no-op 不发空包。

### D — 双发行包流程、集成回归与试点（#195）
按最新实际代码集成 Kit/DSH（若已完成）、受控 tag/release 执行、发布后真实资产核查；覆盖补丁、功能、重大变更，阻塞/回退/中断恢复，README/版本记录/升级文档同步。先在模拟仓库测试，不盲目为测试创建真实 Release。

## 7. 明确非目标和失败准则

不为形式而发空版本、不把每个 commit 自动发布、不承诺无人运行时持续后台执行、不允许自动绕过人工授权、测试 G 门或审查独立性、不根据文件数量决定版本、不把 Format 与 Release 强行同步。不允许发布资产与 tag 不一致、不允许把尚未完成的 DSH 功能写成已发布。缺可信 API、CI、权限、版本或人工决定时只能 STOP/NEEDS_HUMAN_DECISION。

正式启用条件：相关设计文稿审查合并、Owner 常设授权确认、兼容性改动经过负向/旧版升级测试、双底座核验与真实发布过程验收。
