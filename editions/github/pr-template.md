# PR-TEMPLATE.md — github 底座审查包

PR 描述是审查入口，不是完成宣言。下列小节都必须填写；不适用的写“无”，不要留空。

## 批次信息

批次交付时必填；单任务交付写“单任务，不适用批次”。

| 任务 ID | 状态 | head SHA | 验收结果 | 证据链接 |
| --- | --- | --- | --- | --- |
| `<ID>` | `TASK_VERIFIED` / `INTEGRATED` 等批内阶段 | `<完整 commit SHA>` | 逐条 AC 通过 / 未通过 | Issue / PR 评论 / 日志定位 |

- 批次风险等级与理由：`L0`–`L3`，由 `scripts/delivery_risk.py` 按真实 Diff 计算，不采信执行者自报。
- 本 PR 是该批次**唯一**的最终 PR；逐任务 PR 不作为合并对象。
- 合并后验证状态：未执行 / 执行中 / 通过（附命令、退出码与主分支 SHA）；未通过时不得写 `VERIFIED`。

## 做了什么

- 用结果语言说明变更，而不是逐文件复述。
- 对应 Issue 的验收条目编号。
- 如有偏离原方案，说明原因。

## 怎么验证

- 逐条贴出**真实执行过的命令与输出**（含退出码）；CI 链接必须对应当前 head SHA。
- 说明哪些检查在本地跑过、哪些只由 CI 跑。
- 未执行的检查写“未验证”，不得写“应该通过”。

## 没做什么

- 明确列出本次未覆盖的行为、边界与后续任务。
- 已知限制与暂时绕过的地方。
- 若删除了断言、新增了跳过或放宽了检查，必须在此说明理由与批准记录。

## 风险

- 回归风险、数据迁移、权限 / 安全、依赖变化、公开行为变化。
- 回退方式。
- 需要项目所有者决定的事项（有则同时把 Issue 标为 `NEEDS_HUMAN_DECISION`）。

## 关联 Issue

- `Closes #<number>` 或 `Refs #<number>`。
- 依赖的 Issue 编号及当前状态。
- 相关设计文档或前置 PR。
